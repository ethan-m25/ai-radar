Simon Willison: every agent / API needs a default hard budget cap

Hey clawii — you just ran your first local decision model yesterday. Simon Willison is shouting today: "default hard budget caps" — not soft warnings, hard cutoffs that return errors. 453 points, 221 comments on HN. This isn't theory. This is the problem you'll hit next week.

📍 Context: You're already running Clef / Jev decision models locally. But some agents hit APIs (your Claude Code calling OpenAI, or n8n chaining MCP tools). Without a hard cap on those API calls, a runaway agent loop can burn through a month of budget in 5 minutes. This isn't a threat — it's already happening. Muse agents made real mistakes in production. Simon Willison's blog post today is a loud, clear warning.

Why this matters

  • From "fun" to "real risk": You just learned to vibe-code agents. The next problem is agent runaway costs. A hard cap is insurance.
  • What it means for a non-developer: You don't need to understand API rate limits. You just need one setting: "stop if I hit $50 this month."
  • Product gap: Almost no AI platform ships hard caps by default. OpenAI / Anthropic only offer soft reminders.
  • Direct warning for heavy users like you: The more you use Codex, Claude Code, ChatGPT API, the higher your chance of a bill shock at month-end.

🎯 What you can do today

  1. Log into your OpenAI API account: go to platform.openai.com/account/limits and set a hard usage cap (if available; if not, use a third-party wrapper like budget-cli or write your own).
  2. If you use n8n / Workato or other automation platforms, check for "execution timeout" and "credits limit" settings. If none exist, wrap calls with a webhook that checks a counter.
  3. Mention this to your IT department: enterprise agent deployments should consider hard cap features.

How to implement yourself: If you're using the API directly, add a counter check (Redis or local file) before every request — throw an exception if the threshold is exceeded. If you're using a chat interface, you're at the mercy of the platform.

How hard to use: DIY protection for local agents is easy — 10 lines of code. But true "system-level default hard caps" require OpenAI / Anthropic to ship them. We can only push them.

Honest caveat: Hard caps can cause false positives — you might hit the limit during a legitimate workflow and lose context. Simon's proposal: "default hard cap, but users can override with informed consent."

🔭 Watch for: If this HN thread keeps momentum, expect OpenAI / Anthropic to respond within 1-2 weeks. Watch their changelogs for "hard usage cap" additions.

Agents don't need memory — they need documentation

Hey clawii — this HN thread is really interesting. 194 points, 107 comments. The argument: agents mess up not because they lack memory, but because they lack documentation. This perspective is directly useful for a non-developer orchestrating agents.

📍 Context: You started running decision models locally yesterday. You probably hit the "agent forgetfulness" problem in your first round — it loses track after a few steps. Conventional wisdom says "add more memory." This post argues differently: agents need a manual (documentation), just like humans. Their behavior rules, tool usage, and current state should be presented as a document, not buried in a prompt.

Why this matters

  • A philosophy you can use today: When your agent behaves wrong, you might add more prompt or try to enhance memory. Maybe you just need a better "user manual" for it.
  • Practical approach: The author proposes "agent documentation" — a standalone markdown file the agent references on every iteration, instead of relying on conversation history.
  • Direction of impact: If this works, it lowers the barrier for agent orchestration and wastes fewer tokens.

🎯 What you can do today

  1. Read the post (link below) to understand the difference between "agent documentation" and "memory."
  2. If you're tuning an agent, try this: create an AGENT_README.md describing behavior rules, available tools, and output format. Include it as part of the system prompt.
  3. Observe whether the agent is more stable. If it works, write a short note to share.
🔬 Deep dive — what's the actual difference between memory and documentation?
DimensionTraditional memory approachDocumentation approach
Data sourcePrevious conversation historyA standalone, unchanging document
Update methodAuto-appended each turnManual update or version control
Token costGrows over time, gets expensiveFixed size, predictable
StabilityProne to drift (forgetting)Stable, always consistent
Best forChat, open-ended tasksWorkflows with clear rules

How to implement: Add a line to the system prompt: "Before each action, read AGENT_README.md." Have the agent reference the document at every step. The doc itself can be markdown with sections like: ## Goal / ## Available Tools / ## Code of Conduct / ## Output Format.

How hard to use: Trivial. Write a markdown file. 5 minutes.

🔭 Watch for: Will this thread spawn an "agent documentation engine" — a tool that auto-generates and maintains agent docs? Next step: agents that can modify their own docs (self-documenting agents).
