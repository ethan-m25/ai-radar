🚨 The routing era after Fable: stop throwing every task at the most expensive model

model routing · cost optimization · enterprise · pricing strategy
📌 Context

For the past year, you've probably been used to "one model for everything" — Claude, GPT, Gemini, whatever works. But after Anthropic released Fable 5, the game changed: it's incredibly capable, but also incredibly expensive. An FT report (554 points / 490 comments on HN) and Simon Willison's deep dive both point to the same trend — routing is becoming the most practical cost-saving strategy of H2 2026. AT&T has publicly stated that 40% of its AI usage goes through open models, targeting 60-70%, cutting costs by 56% with only a 2% quality drop. This isn't theory — it's what large companies are doing with real money.

WHY THIS MATTERS
  • Direct savings: Fable 5 API pricing can be 3-5x that of Opus 5. Route simple tasks (summarization, classification, extraction) to cheap models and complex tasks to expensive models — your bill can drop by more than half.
  • What it means for non-developers: When you vibe-code with Claude Code or Codex, the underlying system is already doing routing. Understanding this trend explains why some tasks "feel dumber" — it's not model regression, it's being routed to a cheaper tier.
  • Enterprise validation: AT&T at 45B tokens/day, 56% cost reduction, 2% quality drop. This proves routing isn't "saving pocket change" — it's "saving real money without dropping the ball."
  • Ramp AI Index emerges: A new index using credit card billing data from 70,000 companies to estimate model adoption. "Model spend" is becoming a quantifiable management metric.
🎯 ACTION
  1. Read Simon Willison's breakdown: He mapped Anthropic model spend distribution (Opus 4.8 at 28%, Fable 5 at just 8%) — you'll see how large companies actually allocate budget.
  2. Check your vibe coding tool settings: Claude Code and Codex both have model selection options. Pin simple tasks (document cleanup, email drafts) to cheap models (Haiku, Flash), and save expensive models (Opus, Fable) for complex work.
  3. Try a routing tool: OpenRouter already supports automatic routing, and Vercel is pushing it too. If you use APIs for automation, spend 10 minutes configuring routing rules and compare your bill at end of month.
🔬 DEEP DIVE: how routing actually works

vs manually picking models: Right now you probably switch models per task manually. Routing is automatic — the system decides which model to use based on task complexity, context length, and required capabilities. OpenRouter's auto-routing, Anthropic's prompt caching, and OpenAI's smart routing all do this.

AT&T's specific approach: 45B tokens/day, 40% via open models (Qwen, Llama, DeepSeek), targeting 60-70%. They found open models are good enough for "medium-complexity tasks" at a fraction of the cost of closed models. This isn't an "open vs closed" ideology debate — it's pure cost math.

Practical value for someone like clawii: Say your monthly API bill is $200. With routing optimization, it could drop to $80-100 with almost no quality loss. If you use Claude Code, you can set rules like "simple tasks use Haiku, complex tasks use Opus."

Honest caveats: 1) Routing requires some configuration — not plug-and-play. 2) When routing misjudges, a simple task sent to a cheap model might occasionally underperform. 3) If your usage is small (under $50/month), the savings may not be worth the effort.

👀 WATCH FOR
  • Will OpenRouter / Vercel make routing smarter and cheaper?
  • Will Anthropic ship an official routing tool (like "auto-select model")?
  • Will AT&T hit its 60-70% open-model target, and will other large companies follow?
📖 Jargon decoder: Model routing — Automatically selecting the best AI model for each task based on its characteristics, rather than using the same model for everything. Like choosing between a highway and local roads depending on traffic conditions.

👀 Bun 1.4 WebView: browser automation for local agents, absurdly cheap

Bun · browser automation · local agent · dev tools
📌 Context

You've probably used Claude Code or Codex to write code, but "having an agent open a browser, interact with a page, and scrape data" has always been expensive — you need a full Chrome instance, 1-2GB of RAM, plus Playwright or Puppeteer. Bun 1.4 just dropped (first stable release after the Rust rewrite) and it ships with Bun.WebView — browser automation using macOS WebKit or a local Chromium process, needing only 192-256MB of RAM. Simon Willison had Claude Code build a prototype to verify it, and the results were striking.

WHY THIS MATTERS
  • Cost of browser automation for local agents plummets: Used to need 1-2GB RAM per browser agent; now ~200MB. You can run multiple browser agents on your own machine without it slowing down.
  • What it means for non-developers: When vibe-coding, you can tell an agent "open this webpage → extract data → organize into a spreadsheet." That used to be expensive and slow. Now it's cheap enough to run on a whim.
  • Bun 1.4 itself is a big release: Rust rewrite means 50% faster startup, 35% less memory, 2,900 bug fixes. If you use JavaScript/TypeScript for automation, Bun is worth a fresh look.
  • Simon Willison personally validated it: He had Claude Code build a prototype using Bun.WebView to load pages and execute JS — 192-256MB was enough to run a full Chrome.
🎯 ACTION
  1. Upgrade Bun: If you use Bun, run bun upgrade to v1.4. If you've never used Bun, it's a Node.js alternative — installs with one command.
  2. Try Bun.WebView: Run bun install bun then a simple WebView example to see how fast it loads pages and executes JS.
  3. Have Claude Code write you a browser automation script: Tell it "use Bun.WebView to open example.com, extract the title and all links" — see if it works end to end.
🔬 DEEP DIVE: how Bun.WebView is different from Playwright

vs Playwright / Puppeteer: Playwright is a standalone browser automation library that needs a separate browser download (Chromium ~300MB+) and has high memory usage. Bun.WebView is built into Bun, uses the system's native WebKit (macOS) or a local Chromium via CDP, and needs only 192-256MB of RAM with faster startup.

What it runs on: Bun 1.4, rewritten in Rust, with built-in WebView support (macOS WebKit + Chrome DevTools Protocol). No extra browser driver needed.

How hard to use: If you know JavaScript/TypeScript, you can get a first example running in 10 minutes. If you don't know JS, have Claude Code write it for you — it's very good at this.

What you can actually do with it: Say you need to scrape a niche industry website every day. Write a Bun.WebView script, run it on your own machine, low memory footprint, won't bog you down, and you can schedule it to run periodically.

Honest caveats: 1) Bun.WebView is very new — the API may be unstable. 2) WebKit and Chromium behave differently on some sites. 3) If you don't use JavaScript, this tool has limited value for you.

👀 WATCH FOR
  • Will Bun.WebView's API stabilize and see widespread community adoption?
  • Will non-developer-friendly wrappers emerge (like "describe in natural language, auto-generate browser automation script")?
📖 Jargon decoder: WebView — An embedded browser engine inside an app, used to display web pages or perform web operations. Bun.WebView lets developers do browser automation without installing a full browser.

👀 Ornith-1.5: MIT-licensed open model family — 9B, 35B, and 397B all at once

open model · MIT license · multi-tier · local deployment
📌 Context

In the world of open models, you usually have to choose between "small (runs locally but dim)" and "big (smart but won't fit on your GPU)." Ornith-1.5 breaks that trade-off — it ships three sizes at once: 9B dense, 35B MoE, and 397B MoE, all under the MIT license (the most permissive open-source license — use it for anything, including commercial). It also comes in FP8, GGUF, MLX, and NVFP4 quantization formats, covering everything from a phone to a server. Multiple quantized variants are already on HuggingFace and community momentum is building.

WHY THIS MATTERS
  • One family covers every scenario: 9B runs on a laptop, 35B runs on a desktop GPU, 397B runs on a server. You don't have to switch between model families — they share the same behavior and conventions.
  • MIT license = use it however you want: More permissive than Qwen's Apache 2.0. Commercial use, modification, closed-source distribution — all fine. For enterprises, this is the most hassle-free license.
  • End-to-end self-improvement capability: Ornith demonstrates self-improvement — the model can generate its own training data, evaluate itself, and iterate. This is a frontier direction for open models.
  • All quantization formats ready: FP8, GGUF, MLX, NVFP4 — every major format is covered. If you use Ollama, LM Studio, or MLX, you can run it today.
🎯 ACTION
  1. Check HuggingFace: Search for "ornith-ai/Ornith-1.5" and look at the 9B and 35B GGUF variants. Try pulling one with Ollama or LM Studio.
  2. Compare against Qwen3.8-27B: If you're already using Qwen3.8-27B, run the same test prompts and see how Ornith-1.5-35B compares.
  3. Watch for 397B API availability: If you need the strongest open model, check whether Together AI or Fireworks has already deployed Ornith-1.5-397B as an API endpoint.
🔬 DEEP DIVE: how Ornith-1.5 is different from Qwen3.8-27B

vs Qwen3.8-27B: Qwen3.8-27B is a dense model (all 27B parameters active per inference). Ornith-1.5-35B is MoE (35B total, ~3B active). MoE's advantage is faster inference and lower memory usage, though quality may be slightly below a same-parameter-count dense model. Ornith's selling point is "one family, multiple tiers" + MIT license; Qwen's selling point is "single-model peak performance" + Apache 2.0.

What it runs on: Ornith-1.5 supports FP8, GGUF, MLX, NVFP4 quantization formats. Ollama, LM Studio, MLX, and vLLM all work. The 9B variant runs on a Mac with 8GB RAM; 35B needs 16-24GB RAM.

How hard to use: If you use Ollama, ollama pull ornith-1.5-9b is one command. If you use LM Studio, search for "Ornith-1.5" in the interface and download.

What you can actually do with it: Say you want a local "document classification agent" — the 9B version is fast, lightweight, and good enough. If you need "code generation," the 35B version is a better fit.

Honest caveats: 1) Ornith is relatively new — community benchmarks are thin and real-world performance needs validation. 2) The 397B MoE has huge total parameters but only ~3B active (35B variant), which means it may underperform a dense model of the same size on some tasks. 3) MIT license is permissive, but whether the model actually delivers on its claims needs hands-on testing.

👀 WATCH FOR
  • Where does Ornith-1.5 rank on Artificial Analysis and other leaderboards?
  • Will any KOL (Simon Willison, swyx) publish a review of Ornith-1.5?
  • Will Together AI or Fireworks offer the 397B variant as an API?
📖 Jargon decoder: MoE = Mixture of Experts — a model architecture where total parameters are large but only a subset activate per inference, making it fast and memory-efficient. Think of a company with many employees, but only a few work on any given task.
