Qwen 3.8 Flash Next (125B) runs on an RTX 4090 at 100 tokens/s

Hey clawii — you were wondering yesterday what hardware you'd need to run a big model locally. Today HN has your answer: someone verified Qwen 3.8 Flash Next running on a single RTX 4090 at 100 tokens/s. 819 points, 361 comments. This isn't lab data — it's the community actually benchmarking it on real consumer hardware.

📍 Context: Qwen3.8-Flash-Next is the open-source MoE model Alibaba's Qwen team released at the end of August — 180B total parameters, roughly 6B active per token. It used to be considered a high-end-server model. But the community, through quantization (GGUF) and optimizations, got it running at usable speeds on a consumer GPU. For a non-developer this means: you can run a near-frontier open model on your own machine, no cloud API needed.

Why this matters

  • Consumer hardware running frontier models is now real: An RTX 4090 isn't cheap (~$1,600–2,000), but against long-term cloud API costs, a one-time purchase can win. 100 tokens/s is plenty for chat, code completion, and document analysis.
  • What it means for a non-developer: You don't need to understand quantization. The community already publishes GGUF model files that work with Ollama or llama.cpp out of the box. Download one file and use it locally like ChatGPT.
  • Privacy and cost win: Local means your data never leaves the machine. No API bills, no rate limits.

🎯 What you can do today

  1. If you have an RTX 4090 (or 4080/3090), install Ollama and try ollama run qwen3.8-flash-next (if supported) or grab the GGUF file directly from Hugging Face.
  2. No high-end GPU? Keep an eye on community progress for RTX 4060 / 4070 — more aggressive quantization might get this running on lower VRAM too.
  3. Read the HN thread to see the exact quantization recipe and performance tuning tricks people used.

How it works: The key is the MoE (Mixture of Experts) architecture — each inference step only activates a fraction of the parameters (~6B), so compute stays low despite the huge total size. Add 4-bit quantization, which shrinks the 180B model to ~90GB, then KV cache optimization and speculative decoding push it to 100 tokens/s inside 24GB of VRAM.

How hard to use: Medium. If you know Ollama, it's one command. If you need to grab the GGUF and configure llama.cpp yourself, budget 30 minutes. The community has already packaged the easy path.

Honest caveat: 100 tokens/s is a peak number under a specific quantization scheme and prompt length. Real-world use (long context, multi-turn) will be slower. And a 4090 is genuinely expensive for an individual.

🔭 Watch for: Does this thread spawn a wave of consumer-hardware MoE deployment guides? Next checkpoints: a smaller official Flash variant, and whether the community can squeeze this onto 16GB cards.

Jargon decoder: MoE = Mixture of Experts — a model architecture that only activates a subset of parameters per token, so it's fast and cheap to run. GGUF = the standard quantized model format used to run LLMs on consumer hardware. Speculative decoding = a speed-up trick where a small model drafts tokens and the big model just verifies them. KV cache = cached intermediate results during generation that make each next token cheaper.

Decision models like Jev don't beat LLM-as-judge or traditional classifiers

Hey clawii — you've probably been hearing about Jev, the "decision model." Today a Red Hat evaluation on HN says Jev doesn't beat LLM-as-judge or traditional classifiers on standard tasks. 74 points, 23 comments. This isn't "Jev is useless" — it's a reminder that decision models need the right evaluation frame before you trust the hype.

📍 Context: Jev is the decision model the community got excited about recently (autotrust/JEV-27B) — fast, calibrated decisions with full reasoning. But Red Hat's evaluation — literally titled "Decision models like Jev don't beat LLM-as-judge or traditional classifiers" — finds that on standard classification tasks, Jev underperforms both a plain LLM-as-judge (just asking the LLM to judge) and a traditional ML classifier. The takeaway: decision models may fit specific niches, not be a universal replacement.

Why this matters

  • Direct signal if you're Jev-curious: If you were considering Jev for decisions (content moderation, quality scoring), this evaluation says it may not be the best tool.
  • Bigger lesson: New model paradigms get overhyped fast. This paper is a cold shower: don't trust a new paradigm on vibes — benchmark it.
  • For a non-developer: You don't need the technical detail, but you need the reflex: when someone sells you on a "decision model," ask "how does it compare to LLM-as-judge?"

🎯 What you can do today

  1. Read the Red Hat evaluation (link below) and note which tasks and metrics they used.
  2. If you're already using Jev or something like it, run your own head-to-head on your data: Jev vs LLM-as-judge vs a simple classifier.
  3. Follow the follow-ups — the community may find the niche where Jev genuinely wins (e.g. tasks that need calibrated probabilities).

Evaluation details: Red Hat tested Jev across several classification tasks — sentiment analysis, intent recognition, and similar. Jev's accuracy came in below a plain GPT-6 Luna-as-judge and below a simple XGBoost classifier. Jev's real strength is calibrated probability output — the model knows when it's uncertain — which matters in high-stakes settings even if raw accuracy is lower.

How hard to replicate: Easy to try for yourself if you code a little: the Jev model is on Hugging Face and loads with the transformers library. Building the comparison harness takes some scripting.

🔭 Watch for: Will the Jev team respond? Will the community find the niche where Jev actually wins — for example, high-risk decisions that need calibrated confidence (medical triage, financial risk)? If it wins there, it still has real value.
