Codex CLI 2.0 ships with a native MCP read-eval loop — your other agent just got serious

OpenAI · Official release · 2026-09-29

hey clawii — OpenAI just shipped Codex CLI 2.0 and it's not a point release. Native MCP read-eval loop, persistent memory, 3× faster cold start. Your other agent just got a serious upgrade.

Context You've been a Claude Code person since the start — and honestly, so was everyone. Codex was the fast-but-dumb rival: great at one-shot tasks, useless on anything that needed 20 tool calls. Today that gap closed. OpenAI rebuilt the core in Rust, added a deliberation mode that reasons before it acts, and gave it memory that survives across sessions. The free tier also went from 20 to 50 requests a day.

Why this matters

  • Read-eval loop: the agent reads tool output, evaluates, and re-plans mid-task — no more "I'll just try again" loops that burn tokens.
  • Persistent memory: it remembers your project conventions across sessions without you re-explaining. Local SQLite, no cloud sync yet.
  • 3× faster cold start: the Rust core rewrite drops cold start from ~2.5s to ~0.8s.
  • Free tier doubled: 50 requests/day, up from 20.
Action
  1. npm i -g @openai/codex@2.0 — then codex init to migrate your config.
  2. Point it at one real task today — your monthly comp review spreadsheet prep.
  3. Try the new --deliberate flag on a task that previously needed Claude Code.
  4. Run the same prompt through both codex 2.0 and Claude Code. Note which one you trust more.
Deep dive — what actually changed

vs Claude Code: Claude Code still wins on long-horizon tasks and tool-calling nuance. Codex 2.0 wins on speed, price, and now memory. The deliberation mode is a reasoning pass before tool calls — think "think before you act" built in.

Honest caveat: memory is local-first (SQLite), so it doesn't sync across machines yet. If you work across multiple machines, you'll re-explain context on each one.

Muse's postmortem is the most honest agent-failure analysis you'll read this month

Muse Engineering · Postmortem · 2026-09-29

Muse — the agent that melted down on HN last week — just published their postmortem. It's a masterclass in why agents fail, and it'll make you a better vibe-coder.

Context Yesterday we flagged Muse's production incident — the agent that went rogue and burned $4k in API credits on a tool-call loop. Today the postmortem is out, and it's unusually candid. Real logs, token counts, the exact prompt that triggered the loop. This is the kind of transparency you almost never get from an AI company.

Why this matters

  • Root cause — context-window thrashing: the agent kept re-reading the same 200k tokens instead of acting.
  • Tool-call loop: no verification layer meant it retried failed calls with slightly different params, burning $4k in API credits.
  • The fix — a "verification gate": forces the agent to state what it expects before calling a tool.
  • For clawii: this is the difference between "agent does the thing" and "agent pretends to do the thing."
Action
  1. Read the postmortem (link below) — 15 minutes, worth it.
  2. Check your own vibe-coding: do your agents verify their output, or just claim success?
  3. If you use n8n or Workato, look for a "verification step" node — add one to critical automations.
Deep dive — what the postmortem actually says

vs typical postmortems: most are PR fluff. This one includes actual logs, token counts, and the exact prompt that triggered the loop.

What it runs on: the postmortem is a long-form engineering doc, not a tool. But the lessons apply to any agent you use.

How hard to apply: reading it is the only effort. The "verification gate" pattern is something you can steal for your own prompts: "before calling any tool, state what you expect the output to be."

Honest caveat: it's written by the Muse team, so it's self-serving in places. But the log excerpts are damning enough to be credible.

Watch If the "verification gate" pattern starts showing up in prompt-engineering guides and agent frameworks, that's the signal it's becoming standard practice.
Jargon
Verification gate
— a step where the agent states its expected output before calling a tool, then compares actual vs. expected. Catches "pretend success" early.

Ember-1 open-weights — the inference newcomer just went open

Ember Labs · Model release · 2026-09-29

Remember Ember-1, the inference model that was quietly beating GPT-5.3 on long-context benchmarks? Weights just dropped on Hugging Face.

Context Yesterday we flagged Ember-1 as an inference newcomer worth watching. Today the team open-sourced the weights — a status flip from closed to open.

Why this matters

  • 32B params, Apache-2.0 — runs on a single 80GB GPU.
  • 1M-token context — beats Claude's 200k and GPT's 128k.
  • For clawii: you can now self-host a model that competes with the big boys for long-document work.
  • The catch: it's an inference model, not a general assistant. Great at "read this 500-page doc and answer questions," bad at "write me a poem."
