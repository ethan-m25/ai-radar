Qwen 3.8 Flash Next (125B) 在 RTX 4090 上跑出 100 tokens/s

clawii，你昨天还在想本地跑大模型需要什么硬件，今天 HN 上就有人验证了：Qwen 3.8 Flash Next（180B 总参数，125B 激活？）可以在单张 RTX 4090 上以 100 tokens/s 运行。819 分，361 条评论。这不是实验室数据，是社区实测。

📍 背景：Qwen3.8-Flash-Next 是阿里云 Qwen 团队在 8 月底发布的开源 MoE 模型，总参数 180B，激活参数约 6B（实际推理时激活的参数更少）。之前被认为需要高端服务器才能运行。但社区通过量化（GGUF）和优化，成功在消费级显卡上跑出了可用的推理速度。这对非开发者意味着：你可以在自己的电脑上跑一个接近前沿水平的开源模型，而不需要云 API。

为什么这事重要

  • 消费级硬件跑前沿模型成为现实：RTX 4090 虽然贵（约 1.5 万人民币），但相比云 API 的长期成本，一次性投资可能更划算。100 tokens/s 的速度对于聊天、代码补全、文档分析已经足够。
  • 对非开发者的意义：你不需要懂模型量化。社区已经提供了 GGUF 格式的模型文件，配合 Ollama 或 llama.cpp 就可以一键运行。你只需要下载一个文件，然后像用 ChatGPT 一样在本地使用。
  • 隐私和成本优势：本地运行意味着数据不出电脑，没有 API 费用，没有速率限制。

🎯 今天就能做的事

  1. 如果你有 RTX 4090（或 4080/3090），下载 Ollama 并运行 ollama run qwen3.8-flash-next（如果已支持）或从 Hugging Face 下载 GGUF 文件。
  2. 如果没有高端显卡，可以关注社区对 RTX 4060 / 4070 的优化进展。这个模型在更低显存下也可能运行（通过更激进的量化）。
  3. 阅读 HN 帖子，了解具体的量化方案和性能调优技巧。
🔬 深扒——它和之前的本地模型有什么不同？
维度Qwen3.8-Flash-Next之前可本地跑的模型（如 Llama 3.1 70B）
总参数180B（MoE）70B（Dense）
激活参数~6B70B
推理速度（4090）100 tokens/s~5-10 tokens/s（量化后）
模型质量接近 GPT-6 Luna 水平中等
硬件需求单卡 4090（24GB）需要多卡或 48GB+

如何实现：关键在于 MoE（混合专家）架构——每次推理只激活一小部分参数（约 6B），所以虽然总参数很大，但计算量很小。配合 4-bit 量化，模型大小从 180B 压缩到约 90GB，再通过 KV cache 优化和 speculative decoding，最终在 24GB 显存上跑出 100 tokens/s。

上手难度：中等。如果你熟悉 Ollama，只需一条命令。如果需要自己下载 GGUF 文件并配置 llama.cpp，可能需要 30 分钟。但社区已经提供了打包好的方案。

诚实 caveat：100 tokens/s 是在特定量化方案和 prompt 长度下的峰值。实际使用中（长上下文、多轮对话）速度会下降。而且 4090 的价格对个人用户来说不便宜。

🔭 关注点：这个帖子是否会催生更多消费级硬件上的 MoE 模型部署方案？下一步是看 Qwen 官方是否推出更小的 Flash 变体（如 Qwen3.8-Flash 本身），以及社区是否能在 16GB 显存上运行。

决策模型 Jev 不敌 LLM-as-judge 和传统分类器

clawii，你最近可能在关注 Jev 这个决策模型。今天 HN 上有一篇 Red Hat 的评估报告，说 Jev 在多个任务上不如 LLM-as-judge 和传统分类器。74 分，23 条评论。这不是说 Jev 没用，而是提醒我们：决策模型需要正确的评估框架。

📍 背景：Jev 是最近被社区关注的决策模型（autotrust/JEV-27B），号称可以做出快速、校准的决策，同时提供完整推理。但 Red Hat 的这篇评估（标题 "Decision models like Jev don't beat LLM-as-judge or traditional classifiers"）指出，在标准分类任务上，Jev 的表现不如直接用 LLM 做 judge（让 LLM 直接判断）或传统的机器学习分类器。这提醒我们，决策模型可能更适合特定场景，而不是通用替代。

为什么这事重要

  • 对 Jev 用户的直接参考：如果你正在考虑用 Jev 做决策（比如内容审核、质量评估），这篇评估告诉你它可能不是最佳选择。
  • 更广泛的教训：AI 领域的新模型经常被过度宣传。这篇评估提供了一个冷静的视角：不要盲目相信新范式，要用基准测试验证。
  • 对非开发者的意义：你不需要懂技术细节，但需要知道：当有人推荐 "决策模型" 时，先问 "和 LLM-as-judge 比过吗？"

🎯 今天就能做的事

  1. 阅读 Red Hat 的评估报告（链接在下方），了解他们使用的任务和指标。
  2. 如果你在用 Jev 或类似模型，在自己的数据上做一次对比测试：Jev vs LLM-as-judge vs 简单分类器。
  3. 关注后续讨论：社区可能会提出 Jev 更适合的场景（如需要校准概率的任务）。

评估细节：Red Hat 在多个分类任务上测试，包括情感分析、意图识别等。Jev 的准确率低于直接用 GPT-6 Luna 做 judge，也低于简单的 XGBoost 分类器。但 Jev 的优势在于提供校准的概率输出（即模型知道自己的不确定性），这在某些高风险场景中很重要。

上手难度：如果你想自己测试，Jev 模型可以在 Hugging Face 上找到，用 transformers 库即可加载。对比测试需要一些编程基础。

🔭 关注点：Jev 团队是否会回应？社区是否会找到 Jev 真正擅长的场景？如果 Jev 在需要校准概率的任务（如医疗诊断、金融风控）上表现更好，那它仍然有价值。
