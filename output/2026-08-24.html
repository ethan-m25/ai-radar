🚨 Fable 之后的路由时代：别再把所有活都丢给最贵模型

模型路由 · 成本优化 · 企业级 · 定价策略
📌 背景

过去一年，clawii 你可能习惯了「一个模型干所有事」——Claude、GPT、Gemini 轮着用，哪个顺手用哪个。但 Anthropic 的 Fable 5 发布后，情况变了：它很强，但太贵。FT 报道（554 分 / 490 条评论）和 Simon Willison 的解读都指向同一个趋势——「路由」（routing）成为 2026 下半年最实际的省钱策略。AT&T 已经公开说 40% 的 AI 用量走开源模型，目标 60-70%，成本降 56%，质量只掉 2%。这不是理论，是大公司在真金白银地做。

💡 为什么重要
  • 直接省钱：Fable 5 的 API 价格可能是 Opus 5 的 3-5 倍。把简单任务（总结、分类、提取）路由到便宜模型，复杂任务才用贵模型，账单能砍一半以上。
  • 对非开发者的意义：你 vibe coding 时用的 Claude Code / Codex，底层已经在做路由了。理解这个趋势，你就知道为什么有些任务「感觉变笨了」——不是模型退步，是它被路由到了便宜档位。
  • 企业级验证：AT&T 45B tokens/天，成本降 56%，质量只掉 2%。这个数据说明路由不是「省小钱」，是「省大钱且不掉链子」。
  • Ramp AI Index 出现：用 7 万家公司信用卡账单数据估算模型采用率，说明「模型花销」正在变成可量化的管理指标。
⚡ 行动建议
  1. 读 Simon Willison 的解读：他整理了 Anthropic 模型花销分布（Opus 4.8 占 28%，Fable 5 只占 8%），看完你就知道大公司实际怎么分配预算。
  2. 检查你的 vibe coding 工具：Claude Code 和 Codex 都有模型选择设置。把简单任务（文档整理、邮件草稿）固定到便宜模型（Haiku、Flash），复杂任务才用 Opus / Fable。
  3. 试试路由工具：OpenRouter 已经支持自动路由，Vercel 也在推。如果你用 API 做自动化，花 10 分钟配置路由规则，月底看账单对比。
🔍 深度解析：路由到底怎么工作

vs 手动选模型：你现在可能是「一个任务手动切一个模型」。路由是自动的——系统根据任务复杂度、上下文长度、所需能力，自动决定用哪个模型。OpenRouter 的自动路由、Anthropic 的 prompt caching、OpenAI 的智能路由都在做这件事。

AT&T 的具体做法：45B tokens/天，40% 走开源模型（Qwen、Llama、DeepSeek），目标是 60-70%。他们发现开源模型在「中等复杂度任务」上质量足够，成本只有闭源模型的零头。这不是「开源 vs 闭源」的意识形态之争，是纯成本计算。

对 clawii 的实际价值：假设你每月 API 账单 $200，路由优化后可能降到 $80-100，质量几乎不变。如果你用 Claude Code，可以设置「简单任务用 Haiku，复杂任务用 Opus」的规则。

诚实顾虑：1）路由需要一些配置，不是开箱即用。2）路由判断错误时，简单任务被丢给便宜模型可能偶尔质量不够。3）如果你用量很小（每月 <$50），省下的钱可能不值得折腾。

👀 关注点
  • OpenRouter / Vercel 的路由功能是否变得更智能、更便宜？
  • Anthropic 是否会推出官方路由工具（类似「自动选模型」）？
  • AT&T 的 60-70% 开源目标是否达成，其他大公司是否跟进？
📖 术语卡： 模型路由（routing） — 根据任务类型自动选择最合适的 AI 模型，而不是所有任务都用同一个模型。类似「根据路况选择走高速还是走国道」。

👀 Bun 1.4 的 WebView：本地 agent 跑浏览器自动化，便宜到离谱

Bun · 浏览器自动化 · 本地 agent · 开发工具
📌 背景

clawii 你可能用过 Claude Code 或 Codex 帮你写代码，但「让 agent 自己打开浏览器、操作网页、抓数据」这件事，一直很贵——因为要跑一个完整的 Chrome 实例，内存占用 1-2GB，还得单独装 Playwright 或 Puppeteer。Bun 1.4 刚刚发布（Rust 重写后的第一个稳定版），内置了 Bun.WebView——用 macOS 的 WebKit 或本地 Chromium 就能做浏览器自动化，内存只要 192-256MB。Simon Willison 用 Claude Code 做了个原型验证，效果惊人。

💡 为什么重要
  • 本地 agent 的浏览器操作成本大降：以前跑一个浏览器自动化 agent 要 1-2GB 内存，现在只要 200MB 左右。这意味着你可以在自己的电脑上跑多个浏览器 agent，而不卡机。
  • 对非开发者的意义：你 vibe coding 时可以让 agent「打开某个网页 → 提取数据 → 整理成表格」，以前这个流程很贵很慢，现在便宜到可以随便跑。
  • Bun 1.4 本身是个大版本：Rust 重写后启动快 50%、内存省 35%、修了 2900 个 bug。如果你用 JavaScript/TypeScript 做自动化，Bun 值得重新看一眼。
  • Simon Willison 亲自验证：他用 Claude Code 写了个原型，用 Bun.WebView 加载网页并执行 JS，内存 192-256MB 就够跑完整 Chrome。
⚡ 行动建议
  1. 升级 Bun：如果你用 Bun，跑 bun upgrade 到 1.4。如果你没用过 Bun，它是 Node.js 的替代品，安装只要一条命令。
  2. 试试 Bun.WebView：用 bun install bun 然后跑一个简单的 WebView 示例，看看加载网页和执行 JS 有多快。
  3. 让 Claude Code 帮你写个浏览器自动化脚本：告诉它「用 Bun.WebView 打开 example.com，提取标题和所有链接」，看它能不能跑通。
🔍 深度解析：Bun.WebView 和 Playwright 有什么不同

vs Playwright / Puppeteer：Playwright 是独立的浏览器自动化库，需要单独安装浏览器（Chromium 约 300MB+），内存占用高。Bun.WebView 是 Bun 内置的，用系统自带的 WebKit（macOS）或本地 Chromium，内存只要 192-256MB，启动更快。

跑在什么之上：Bun 1.4 是 Rust 重写后的版本，内置 WebView 支持（macOS WebKit + Chrome DevTools Protocol）。不需要额外安装浏览器驱动。

上手难度：如果你会 JavaScript/TypeScript，10 分钟能跑通第一个示例。如果你不会 JS，让 Claude Code 帮你写，它很擅长这个。

对 clawii 的实际价值：假设你要每天自动抓取某个行业网站的数据，用 Bun.WebView 写个脚本，跑在你自己的电脑上，内存占用小，不卡机，还能定时跑。

诚实顾虑：1）Bun.WebView 还很新，API 可能不稳定。2）WebKit 和 Chromium 的行为有差异，某些网站可能表现不同。3）如果你不用 JavaScript，这个工具对你价值有限。

👀 关注点
  • Bun.WebView 的 API 是否稳定，社区是否开始大量使用？
  • 是否有非开发者友好的封装工具出现（比如「用自然语言描述，自动生成浏览器自动化脚本」）？
📖 术语卡： WebView — 在应用内嵌一个浏览器引擎，用来显示网页或执行网页操作。Bun.WebView 让开发者不用装完整浏览器就能做网页自动化。

👀 Ornith-1.5：MIT 协议的开源模型家族，9B/35B/397B 三档全开

开源模型 · MIT 协议 · 多档位 · 本地部署
📌 背景

开源模型的世界里，你通常只能在「小模型（跑得动但笨）」和「大模型（聪明但跑不动）」之间二选一。Ornith-1.5 打破了这种选择——它一次性发布了 9B（密集）、35B（MoE）、397B（MoE）三个档位，全部 MIT 协议（最宽松的开源许可，随便商用）。而且自带 FP8、GGUF、MLX、NVFP4 等多种量化格式，从手机到服务器都能跑。HuggingFace 上已经出现多个量化版本，社区热度在涨。

💡 为什么重要
  • 一个家族覆盖所有场景：9B 跑在笔记本上，35B 跑在桌面 GPU，397B 跑在服务器。你不用在不同模型之间切换，用同一个家族的模型，行为一致性更好。
  • MIT 协议 = 随便用：比 Qwen 的 Apache 2.0 还宽松，商用、改代码、闭源分发都行。对企业来说，这是最省心的 license。
  • 端到端自我改进能力：Ornith 展示了「自我改进」能力——模型可以自己生成训练数据、自己评估、自己迭代。这是开源模型的前沿方向。
  • 量化格式齐全：FP8、GGUF、MLX、NVFP4 全都有，意味着 Ollama、LM Studio、MLX 用户都能直接跑。
⚡ 行动建议
  1. 去 HuggingFace 看看：搜「ornith-ai/Ornith-1.5」，看看 9B 和 35B 的 GGUF 版本，用 Ollama 或 LM Studio 跑一下试试。
  2. 对比 Qwen3.8-27B：如果你已经在用 Qwen3.8-27B，跑几个同样的测试题，看看 Ornith-1.5-35B 的表现差异。
  3. 关注 397B 的 API 服务：如果你需要最强开源模型，看看 Together AI 或 Fireworks 是否已经上线 Ornith-1.5-397B。
🔍 深度解析：Ornith-1.5 和 Qwen3.8-27B 有什么不同

vs Qwen3.8-27B：Qwen3.8-27B 是密集模型（27B 参数全激活），Ornith-1.5-35B 是 MoE（35B 总参数，3B 激活）。MoE 的优势是推理更快、更省显存，但质量可能略低于同参数的密集模型。Ornith 的卖点是「一个家族多档位」+ MIT 协议，Qwen 的卖点是「单模型性能极致」+ Apache 2.0。

跑在什么之上：Ornith-1.5 支持 FP8、GGUF、MLX、NVFP4 量化格式，Ollama、LM Studio、MLX、vLLM 都能跑。9B 可以在 8GB 内存的 Mac 上跑，35B 需要 16-24GB 内存。

上手难度：如果你用 Ollama，ollama pull ornith-1.5-9b 一条命令就能跑。如果你用 LM Studio，直接在界面里搜「Ornith-1.5」下载即可。

对 clawii 的实际价值：假设你要在本地跑一个「文档分类 agent」，9B 版本就够用，跑得快、不占资源。如果你要跑「代码生成」，35B 版本可能更合适。

诚实顾虑：1）Ornith 是相对新的模型，社区评测还不多，实际表现有待验证。2）397B MoE 虽然总参数大，但激活参数只有 3B（35B 版本），某些任务可能不如同参数的密集模型。3）MIT 协议虽宽松，但模型本身的能力是否真的达到宣传水平，需要实测。

👀 关注点
  • Ornith-1.5 在 Artificial Analysis 等评测榜上的实际排名？
  • 是否有 KOL（Simon Willison、swyx）评测 Ornith-1.5？
  • Together AI / Fireworks 是否上线 397B 的 API？
📖 术语卡： MoE = Mixture of Experts — 一种模型架构，总参数很大，但每次推理只激活一部分参数，所以速度快、省显存。类似「一个公司有很多员工，但每个任务只派几个人去做」。
