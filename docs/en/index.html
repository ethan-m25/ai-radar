Qwen 3.8 Flash Next (125B) runs on an RTX 4090 at 100 tokens/s

Hey clawii — HN's front page blew up overnight: someone got Qwen 3.8 Flash Next (125B) running at 100 tokens/s on a consumer RTX 4090. This isn't cloud API numbers — it's a real desktop GPU. 820 points, 363 comments. The bar for "run the biggest open models locally" just dropped hard.

📍 Context: Qwen3.8-Flash-Next is Alibaba's open-weight MoE model from late August — 180B total parameters, ~6B active per token. You've already been running local decision models like Clef and Jev (27B). This is a different weight class entirely: 125-180B used to mean multi-A100 servers or a cloud API bill. Now one consumer GPU (24GB) does the job. "Best open models on your own desk" just went from geek toy to real option.

Why this matters

  • Local = free + private + unlimited calls: Once you can run a 125B-class model locally, you stop caring about API billing and rate limits. For a heavy vibe-coder, that's a quality-of-life shift, not a minor perk.
  • The hardware threshold is now clear: The 4090 is today's consumer flagship, and the 5080/5090 generation is coming. If you're thinking about a GPU upgrade, this is your evidence: one 24GB card is enough.
  • It's verified, not a slide deck: This is a real GitHub project (niko1221) with an actual quant recipe and benchmark, discussed on HN for more than 20 hours. Community-verified, not vendor marketing.

🎯 What you can do today

  1. Open the GitHub project and check which quantization scheme it uses (probably 2-bit or lower).
  2. If you have a 24GB card (4090 / 3090), follow the README and try it. If not, save the link — it's your next-hardware-upgrade checklist item.
  3. Compare your current API monthly bill vs the one-time hardware cost. If local can cover your daily work, it may win long-term.

Key trick: Qwen 3.8 Flash Next is an MoE model — 180B total parameters, but only ~6B are active per token. With 2-bit quantization the weights compress to roughly 40GB, then CPU offloading pushes part of the model into system RAM while the GPU only processes the active layers. That's how 24GB of VRAM is enough.

How hard: Medium. You'll need llama.cpp or vLLM, quantization parameters, and some patience tuning the CPU-offload ratio. Non-developers: budget 1-2 hours to get it running, longer for good tuning.

Honest caveat: 2-bit quantization costs precision. Fine for coding tasks, but heavy reasoning (math, logic) will get noticeably dumber. 100 tokens/s is a peak under a specific config; long contexts and multi-turn chats will be slower.

🔭 Watch for: If the repo clears ~5k stars within a week, the community has validated the recipe and "local big model" becomes a mainstream topic. Also watch for a 5090-generation tuned quant build.

Jargon decoder: MoE = Mixture of Experts — a model architecture that splits into many "expert" subnetworks and only activates a subset per token, saving compute. Quantization = compressing model weights from 16-bit down to 4-bit or 2-bit to shrink the file, at some cost to precision. KV cache = cached intermediate results during generation that make each next token cheaper, but it eats VRAM. CPU offloading = pushing some model layers into system RAM while the GPU handles only the active layers.

Decision models like Jev don't beat LLM-as-judge or traditional classifiers

Hey clawii — you only got Jev running locally last week, and today Red Hat published a hands-on evaluation: decision models don't beat LLM-as-judge or a plain traditional classifier. 76 points, 24 comments. Not "Jev is useless" — more like "the whole category is overhyped until proven otherwise."

📍 Context: Jev (autotrust/JEV-27B) is the "decision model" that got the community excited — fast, calibrated decisions with full reasoning. You started using it for local judgment calls like email triage. Red Hat engineers ran it against LLM-as-judge (using an LLM as the judge) and a traditional classifier on 100 tasks. Result: no statistically significant edge.

Why this matters

  • Don't chase novelty for novelty's sake: The time you spent learning Jev might be better spent elsewhere if it doesn't outperform simpler tools.
  • Lesson for non-developers: Not every new AI buzzword deserves your attention. Rules and simple classifiers can be more reliable and a lot cheaper.
  • Concrete numbers, not vibes: Red Hat published the comparison tables and method. You can judge for yourself.

🎯 What you can do today

  1. Read the Red Hat evaluation. Check which tasks and metrics they used.
  2. If you use Jev for classification, run your own head-to-head with a simple classifier (e.g. scikit-learn logistic regression).
  3. Don't uninstall Jev — it may still win where you want explanations + local + fast + calibrated probabilities. Just stop treating it as a universal answer.

Red Hat's core finding: on 100 tasks, Jev and LLM-as-judge showed no statistically significant accuracy difference, and traditional classifiers held their ground when there was enough labeled data. Jev's real edge is being local, fast, and interpretable — plus calibrated probabilities. If you don't care about those, simpler tools are less hassle.

How hard to try yourself: Easy if you code a little — Jev is on Hugging Face and loads with the transformers library. Building a comparison harness takes some scripting, but nothing exotic.

🔭 Watch for: If more institutions publish similar comparisons, the decision-model hype cycle cools. Watch whether the Jev team responds — and whether calibrated-confidence niches (risk, triage) turn out to be where it genuinely wins.
