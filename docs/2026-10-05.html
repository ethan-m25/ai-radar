RTX 4090 上跑 Qwen 3.8 Flash Next (125B) 达到 100 tokens/s

clawii，HN 头条炸了——有人在消费级 RTX 4090 上把 125B 参数的模型跑到了 100 tokens/s。这不是云端，是你自己桌面上的显卡。819 点，361 条评论。你一直想本地跑大模型，现在门槛又降了一大截。

📍 背景：你之前已经在本地跑 Clef / Jev 等决策模型了，那些都是 27B 左右的小模型。但 125B 是另一个量级——之前这需要多张 A100 或者云端 API。现在有人用单张 4090（24GB 显存）做到了。这意味着 "本地跑顶级开源模型" 从极客玩具变成了现实选项。

为什么这事重要

  • 本地 = 免费 + 隐私 + 无限调用：一旦你能在本地跑 125B 模型，你就不再受 API 计费和速率限制的约束。这对你这种重度 vibe coder 是质变。
  • 硬件门槛清晰了：4090 是消费级旗舰，但 5080/5090 也在路上。如果你考虑升级显卡，这个数据点直接告诉你值不值。
  • 技术验证：这不是 PPT，是 GitHub 上的实际项目（niko1221），有具体配置和 benchmark。

🎯 今天就能做的事

  1. 去看 GitHub 项目 github.com/niko1221，看它用的什么量化方案（应该是 4-bit 或更低）。
  2. 如果你有 24GB 显存的卡（4090 / 3090），直接按 README 试跑。没有的话，先收藏，等下次升级硬件。
  3. 对比一下你现在的 API 月费 vs 一次性硬件成本——如果本地能跑，长期可能更划算。
🔬 深扒——125B 怎么塞进 24GB 显存的？
维度Qwen 3.8 Flash Next (125B)你之前跑的 Clef (27B)
参数总量125B（实际 180B MoE，激活 6B）27B
显存需求（FP16）~360GB（不可能本地）~54GB（需要双卡）
显存需求（4-bit 量化）~70GB（仍超单卡）~14GB（单卡可跑）
实际方案2-bit 量化 + 稀疏激活 + KV cache 优化标准 4-bit GGUF
速度100 tokens/s（4090）~50 tokens/s

关键 trick：Qwen 3.8 Flash Next 是 MoE（混合专家）架构，虽然总参数 180B，但每次推理只激活 6B 参数。配合 2-bit 量化，模型权重可以压到 ~40GB，再用 CPU offloading 把一部分层放到内存，GPU 只处理激活层。这就是为什么 24GB 显存能跑。

上手难度：中等。需要装 llama.cpp 或 vLLM，配置量化参数，可能还要调 CPU offload 比例。对非开发者来说，1-2 小时能跑通，但调优需要些耐心。

诚实 caveat：2-bit 量化会损失精度。编码任务可能还行，但复杂推理（数学、逻辑）可能明显变笨。100 tokens/s 是峰值，实际长上下文会掉。

🔭 关注点：如果这个项目 star 数在 7 天内破 5k，说明社区验证了可行性，本地大模型会成为主流话题。另外关注 5090 发布后是否有更好的量化方案。

Red Hat 实测：决策模型（Jev）没比 LLM-as-a-judge 或传统分类器强

clawii，你上周刚在本地跑起来 Jev 决策模型，Red Hat 今天就发了一篇实测说它并没有比传统方法强。74 点，23 条评论。这不是说 Jev 没用，而是说"决策模型"这个新品类可能被高估了。

📍 背景：你上周开始用 Jev 做本地决策（比如判断邮件优先级、分类任务）。Jev 的卖点是"快速、校准良好的决策，不需要完整推理"。但 Red Hat 的工程师用 100 个任务对比了 Jev、LLM-as-a-judge（用 GPT 当裁判）和传统分类器（比如朴素贝叶斯），结果 Jev 并没有显著优势。

为什么这事重要

  • 别盲目追新：你花时间学 Jev，但如果它不比传统方法强，那你的时间可能花在别处更好。
  • 对非开发者的启示：不是所有"AI 新词"都值得追。有时候传统工具（规则、分类器）更可靠、更便宜。
  • 具体数据：Red Hat 给出了对比表格，不是空谈。你可以自己判断。

🎯 今天就能做的事

  1. 读 Red Hat 的原文（链接在下方），看他们的测试方法和具体数据。
  2. 如果你在用 Jev 做分类任务，对比一下用传统方法（比如 scikit-learn 的逻辑回归）的效果。
  3. 别急着卸载 Jev——它在某些场景（需要解释性、本地运行）可能仍有价值，但别把它当万能药。
🔬 深扒——决策模型 vs 传统分类器，到底差在哪？
维度Jev (决策模型)LLM-as-a-judge传统分类器
速度快（~50ms）慢（~1s）极快（~1ms）
成本本地免费API 计费本地免费
可解释性中等（有推理过程）低（黑盒）高（特征权重）
准确率与 LLM-judge 相当与 Jev 相当略低但稳定
适用场景需要推理的决策需要通用判断明确规则、大量数据

Red Hat 的核心发现：在 100 个任务上，Jev 和 LLM-as-a-judge 的准确率没有统计显著差异，而传统分类器在数据充足时表现接近。Jev 的优势在于"本地、快速、可解释"，但如果你不在乎这些，传统方法更省事。

对 clawii 的建议：如果你用 Jev 做的是"需要解释的决策"（比如为什么拒绝这个申请），它有价值。如果只是分类（垃圾邮件/非垃圾），传统方法足够。

🔭 关注点：如果更多机构发布类似的对比测试，决策模型的热度可能会降温。关注 Jev 团队是否回应。
