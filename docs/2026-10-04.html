Simon Willison：所有 agent / API 都需要默认硬预算上限

clawii，你昨天才把第一个本地决策模型拉下来跑起来，Simon Willison 今天就喊出了 "default hard budget caps"——不是软上限，是硬切断，超过就报错。HN 453 点，221 条评论。这不是理论，是你马上就会遇到的问题。

📍 背景：你已经在本地跑 Clef / Jev 等决策模型了。但你很快会发现，有些 agent 是走 API 的（比如你的 Claude Code 调 OpenAI，或者你用 n8n 接 MCP 工具）。如果你不给这些 API 调用设硬上限，一个死循环的 agent 可以在 5 分钟内烧掉你一个月的预算。这不是威胁，是已经发生的事——Muse agent 在真实场景中做错了事。Simon Willison 今天在博客上发出了强烈的警告。

为什么这事重要

  • 从 "有趣" 到 "真实风险"：你刚学会用 vibe coding 调 agent，下一个问题就是 agent 失控的成本。hard cap 是保险。
  • 对非开发者的意义：你不需要懂 API 限流。你只需要一个设置："每月超过 $50 就停"。
  • 产品空缺：目前几乎没有任何 AI 平台默认提供硬上限。OpenAI / Anthropic 只有软提醒。

🎯 今天就能做的事

  1. 检查你的 OpenAI API 账户：去 platform.openai.com/account/limits 设置 "hard usage cap"（如果有的话。如果没有，用第三方工具如 budget-cli 或自己写一个包装）。
  2. 如果你在用 n8n / Workato 等 automation 平台，检查是否有 "execution timeout" 和 "credits limit"。没找到就用 webhook 包装。
  3. 和你的 IT 部门提一句：企业级 agent 部署应该考虑硬上限功能。

实现方式：如果你用的是 API，可以在你的代码中自己实现：每次请求前检查一个计数器（比如 Redis 或本地文件），超过阈值就抛异常。如果你用的是 chat interface，那更危险——只能靠平台方实现。

上手难度：自己实现来保护本地 agent 很简单：10 行代码。但真正的 "系统级默认硬上限" 需要 OpenAI / Anthropic 等厂商去实现，我们只能 push 他们。

诚实 caveat：硬上限可能会误伤——比如你在合法的工作流中达到上限，中断可能会丢失上下文。所以 Simon 建议是 "默认 hard cap，但用户可以在知晓风险的情况下解除"。

🔭 关注点：如果这个 HN 帖子继续发酵，预计 1-2 周内 OpenAI / Anthropic 会回应。关注他们的 changelog 是否加入 "hard usage cap"。

Agents 不需要 memory，它们需要 documentation

clawii，HN 上这个帖子很有意思——194 点，107 条评论，说 agents 搞砸的主要原因不是 memory 不够，而是没有文档。这个观点对你这种非开发者做 agent 编排很有启发。

📍 背景：你昨天开始在本地跑决策模型。你可能在第一轮就遇到了 agent 的 "健忘" 问题——它做了几步之后就不知道自己在干嘛了。传统观点认为这是 memory 不够。但这个帖子提出不同的观点：agent 需要像人一样，有一份说明书 (documentation)。 它的行为规则、工具使用方法、当前状态，应该以文档形式呈现，而不是埋在 prompt 里。

为什么这事重要

  • 对你直接有用的哲学：你在调 agent 时，如果 agent 行为不对，你可能会加更多 prompt 或者想办法增强 memory。但也许你只需要写一份更好的 "使用手册" 给它。
  • 实际方案：作者提出了 "agent documentation" 的概念——一个独立的 markdown 文件，agent 在每次迭代时参考它，而不是靠先前的对话。
  • 影响方向：如果这个方法有效，会降低 agent 编排的门槛，也意味着更少的 token 浪费。

🎯 今天就能做的事

  1. 读这篇帖子（链接在下方），理解 "agent documentation" 和 "memory" 的区别。
  2. 如果你在调 agent，试一下：创建一个 AGENT_README.md，描述 agent 的行为规则、可用工具、输出格式，然后把它作为 system prompt 的一部分。
  3. 观察 agent 是否更稳定了。如果有效，可以写篇笔记分享。
🔬 深扒——memory 和 documentation 到底有什么不同？
维度传统 memory 方法documentation 方法
数据来源先前的对话历史一份独立、不变的文档
更新方式每次对话自动追加手动更新或版本控制
Token 消耗随时间增长，越来越贵固定大小，可预测
稳定性容易 drift（遗忘）稳定，总保持一致性
适用场景闲聊、开放式任务有明确规则的工作流

如何实现：在 system prompt 中加入一行"在每次行动前，阅读 AGENT_README.md"。让 agent 每一步都参考文档。文档本身可以用 markdown 写，包含：## 目标 / ## 可用工具 / ## 行为准则 / ## 输出格式。

上手难度：超级简单。写一个 markdown 文件，5 分钟。

🔭 关注点：这个帖子是否会催生 "agent documentation engine"（自动生成、维护 agent 文档的工具）？下一步是 agent 自己能修改文档（self-documenting agent）。
